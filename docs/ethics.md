# ATLAS — Ethical Considerations

## 1. Intended use

ATLAS is built for **academic research, public-data analysis, synthetic
data demonstration, and educational use**. It is a Final Year Project
demonstrating data engineering, entity resolution, graph analytics,
anomaly detection, NLP, and retrieval-grounded AI assistance -- not a
production intelligence product, and not intended to be deployed as one
without substantial additional review.

## 2. What ATLAS explicitly does not do

The project brief that shaped this build was explicit about this, and
every phase was built to respect it:

- **No covert surveillance.** ATLAS analyzes datasets a user explicitly
  loads; it does not collect, scrape, or monitor data about anyone
  without their knowledge.
- **No unauthorized tracking of real individuals.** The demonstration
  dataset is entirely synthetic (see section 3). ATLAS is not designed or
  tested for use on real personal data, and doing so would require a
  separate, deliberate privacy and legal review that is out of this
  project's scope.
- **No facial recognition or biometric identification.**
- **No hacking, credential collection, or unauthorized access tooling.**
- **No profiling of private individuals.** Entity resolution here links
  *records a user already has*, it does not discover new information
  about a person from external sources.

## 3. Data used

Every dataset shipped with or generated by this project is **synthetic**,
produced by `scripts/generate_data.py` using the [Faker](https://faker.readthedocs.io/)
library. No real person, organization, or event is represented. This is
stated directly in the Streamlit dashboard's sidebar on every page (see
`dashboard/app.py`), not just in documentation that a user might not read.

If ATLAS were ever pointed at real-world data (a legitimate possible use
for the underlying techniques -- e.g. a researcher's own public dataset),
the responsibility for that data's provenance, consent, and legality
belongs to whoever loads it, and such use is outside what this project
was designed, tested, or reviewed for.

## 4. Hedged language as a designed-in ethical control

This is not just a documentation promise -- it is enforced in the code
itself, at every layer that produces a probabilistic judgment:

- **Entity resolution** (`app/processing/entity_resolution.py`) never
  states two records are the same person -- only "potential match",
  "possible match", or "weak possible match" at defined confidence bands.
  See `confidence_label()` and the accompanying tests
  (`test_resolve_entities_never_claims_certainty`).
- **Anomaly detection** (`app/ml/anomaly_detection.py`) never states a
  transaction is fraudulent -- only that it is a "potential anomaly",
  i.e. statistically unusual relative to the rest of the dataset. See
  `test_statistical_never_uses_fraud_language`.
- **The AI assistant** (`app/ai/prompts.py`) is instructed, as a hard
  rule in its system prompt, to preserve this hedging rather than
  simplify it away when explaining evidence in natural language, and to
  separate FACT from INFERENCE from UNCERTAINTY rather than presenting a
  synthesized answer as more certain than its evidence supports.

These aren't stylistic choices -- a tool that outputs "this person is a
fraudster" or "these are definitely the same identity" would misrepresent
statistical similarity as certainty, with real potential for harm if
someone acted on that false confidence. Enforcing the hedging in code and
tests (not just in a README) means it survives refactoring instead of
being one contributor's forgotten convention.

## 5. Limitations that are also ethical considerations

Some of the technical limitations documented elsewhere in this project
are also, directly, reasons for caution about real-world use:

- Entity resolution's recall degrades substantially at scale (see
  `docs/experiments.md`) -- a system tuned for this project's speed
  constraints would miss many true duplicates in a larger, real dataset,
  which matters if duplicate detection were ever relied on for a
  consequential decision.
- Anomaly detection scores are relative to the specific dataset they're
  computed on -- an amount that's anomalous in a dataset of small
  transactions may be unremarkable in a dataset of large ones. A score
  should never be read as an absolute measure of anything.
- The AI assistant's LLM explanation step, when enabled, can still
  misinterpret or oversell retrieved evidence in its own phrasing, even
  under a prompt that instructs it not to (see `docs/defense_questions.md`
  Phase 7 section) -- the fallback analytical mode exists partly because
  a deterministic template has no such risk.

## 6. Data handling

- All processing is local: the dashboard, database, and analytics run on
  the user's own machine (or their own deployment) with no external data
  transmission, except the optional AI assistant's calls to the
  Anthropic API when a key is explicitly configured (see `docs/api.md`
  and `.env.example`).
- Uploaded files are processed in memory / a local SQLite database
  (`data/processed/atlas.db` by default) and are never sent anywhere
  else by ATLAS itself.
- `.env` (containing any real API keys) is gitignored and never committed.

## 7. Academic context

This project was built as a BS Data Science Final Year Project. Its
purpose is to demonstrate technical competence across data engineering,
graph analytics, machine learning, and responsible AI-assistance design
-- explicitly modeled as an *original* platform inspired by the general
category of data-intelligence tools, not a clone of any specific
proprietary product's code, branding, or confidential functionality.

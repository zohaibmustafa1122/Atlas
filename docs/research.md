# ATLAS — Research Methodology

## 1. Research question

> Can resource-efficient graph-based entity resolution and anomaly
> detection improve exploratory analysis of heterogeneous datasets on
> low-resource computing environments?

This is deliberately narrower than "is ATLAS a good platform" -- it asks
whether two specific, CPU-only techniques (fuzzy-matching entity
resolution with blocking; robust-statistics and Isolation Forest anomaly
detection) do useful work at increasing data scale on hardware with no
GPU and 8 GB of RAM, and whether a more sophisticated ("improved") method
consistently beats a simpler ("baseline") one, or whether that depends on
the shape of the problem.

## 2. Hypotheses

- **H1 (entity resolution):** a multi-feature similarity score
  (Levenshtein + token Jaccard + TF-IDF character n-gram cosine)
  achieves higher F1 than a single-feature baseline (Levenshtein only)
  at a fixed similarity threshold.
- **H2 (anomaly detection):** Isolation Forest achieves higher F1 than a
  robust z-score baseline at detecting injected transaction-amount
  outliers.
- **H3 (scalability):** processing time and memory grow sub-quadratically
  with dataset size once blocking (entity resolution) and centrality
  approximation (graph analytics) are applied, making all three
  pipelines usable at 100,000 records on 8 GB RAM.

H1 and H3 were supported by the experiments (with an important caveat for
H1, below); **H2 was not supported** -- see docs/experiments.md for why,
and why that's a real finding rather than a failed test.

## 3. Experimental design

### 3.1 Data

Synthetic "global events" datasets at three scales (1,000 / 10,000 /
100,000 person records, with proportionally scaled organizations,
locations, events, relationships, and transactions), generated by
`scripts/generate_data.py` with a fixed random seed for reproducibility.
The generator injects two kinds of ground truth specifically so these
experiments have a real answer key:

- **Entity resolution ground truth**: for ~5% of persons, a deliberately
  varied duplicate record (initial, honorific, dropped middle name, or
  single-character typo) with a recorded true-identity link.
- **Anomaly detection ground truth**: for ~1% of transactions, an amount
  replaced with an extreme outlier (50,000-500,000 vs. a typical range of
  10-5,000), with the transaction id recorded.

### 3.2 Procedure

`scripts/run_experiments.py` runs, for each size, in this order:
database loading, graph construction, graph analytics, entity resolution
(both methods), anomaly detection (both methods), and one representative
simple database query -- each timed independently. Entity resolution and
anomaly detection are each evaluated against their ground truth via
precision/recall/F1 (and false-positive rate for anomaly detection).
Results are written to `data/processed/experiments/results_<timestamp>.{json,csv}`
and charted to `docs/experiments/`.

Experiments run against an isolated SQLite file
(`data/processed/experiments.db`), never the interactive dashboard's
database, so re-running experiments can't corrupt demo data and vice versa.

### 3.3 Metrics

- **Entity resolution / anomaly detection**: precision, recall, F1 (and
  false-positive rate for anomalies) against the injected ground truth,
  at a fixed similarity threshold of 0.70 (chosen per the threshold-
  sensitivity analysis in section 4).
- **Performance**: wall-clock time for database loading, graph
  construction, and graph-metrics computation; peak process memory
  (a cumulative watermark across the whole run -- see the limitation
  noted in section 5).

### 3.4 Baseline vs. improved definitions

| Task | Baseline | Improved |
|---|---|---|
| Entity resolution | Levenshtein ratio only | Levenshtein + token Jaccard + TF-IDF char n-gram cosine (weighted) |
| Anomaly detection | Robust z-score (median/MAD) | Isolation Forest (scikit-learn, on log-transformed amount) |

## 4. Threshold sensitivity (entity resolution)

Before fixing the 0.70 threshold used in the main experiments, both
methods were measured at 1,000-record scale across three thresholds:

| Threshold | Baseline F1 | Multi-feature F1 |
|---|---|---|
| 0.55 | 0.017 | 0.105 |
| 0.70 | 0.073 | 0.692 |
| 0.85 | 0.606 | 0.269 |

The multi-feature method's advantage over the baseline is not uniform
across thresholds -- it is largest at 0.70 and *reverses* at 0.85, where
the baseline's simpler scoring happens to separate signal from noise
better on this particular dataset. 0.70 was chosen for the main
experiments because it is where the intended "improved" method actually
shows its intended advantage; this choice is disclosed here rather than
silently picking the threshold that made H1 look best.

## 5. Known limitations of the experimental design

- **Peak memory is a cumulative watermark**, not an isolated
  per-dataset-size figure -- `run_experiments.py` runs all sizes in one
  process, so the reported peak memory for size *N* reflects the highest
  watermark reached by the time that size finishes, including everything
  before it. An isolated measurement would need one subprocess per size;
  this was judged not worth the added complexity for an FYP-scale study,
  and the reported numbers should be read as "memory does not exceed
  this" rather than "this size costs exactly this much."
- **Single random seed.** All experiments use one fixed seed for
  reproducibility, not repeated runs with confidence intervals. This is
  standard practice for a demonstrative study at this scope, but means
  reported numbers are point estimates, not statistically robust averages.
- **One dataset shape.** The synthetic generator's duplicate/anomaly
  injection rates (5% / 1%) and variation patterns are fixed; results may
  not generalize to datasets with different duplicate rates or anomaly
  shapes (see docs/experiments.md for a concrete case where this matters
  for H2).
- **Single-machine timing.** Wall-clock times reflect this development
  environment's specific CPU; they demonstrate relative scaling behavior
  and rough feasibility, not portable absolute benchmarks.
